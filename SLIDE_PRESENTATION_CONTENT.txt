SLIDE 15: KIỂM THỬ HỘP TRẮNG vs HỘP ĐEN

Kiểm thử hộp trắng (White-box Testing):
• Định nghĩa: Kiểm tra internal logic của code
• Ngoài dùng: Jest Unit Test
• Mục tiêu: Kiểm tra functions, methods, conditions
• Ví dụ:
  - Kiểm tra validateEmail() function (TC-UM-006)
  - Kiểm tra calculateAverageRating() (TC-RS-002)
  - Kiểm tra filterProducts() (TC-PM-003 → TC-PM-012)
• Lợi ích: Phát hiện lỗi sớm, code coverage cao
• Nhược điểm: Cần hiểu code, tốn thời gian

Kiểm thử hộp đen (Black-box Testing):
• Định nghĩa: Kiểm tra behavior từ user perspective
• Công cụ: Cypress E2E Test
• Mục tiêu: Kiểm tra user flow, UI interaction
• Ví dụ:
  - User login (TC-UM-002 → TC-UM-004)
  - User search products (TC-PM-002)
  - User submit review (TC-RS-003)
• Lợi ích: Gần với real user scenario, không cần code knowledge
• Nhược điểm: Chậm, high maintenance

So sánh:
┌────────────────────┬──────────────────┬─────────────────┐
│ Tiêu chí           │ Hộp trắng         │ Hộp đen         │
├────────────────────┼──────────────────┼─────────────────┤
│ Mục đích           │ Logic validation  │ Behavior check  │
│ Công cụ            │ Jest              │ Cypress         │
│ Tốc độ             │ Nhanh (ms)        │ Chậm (s)        │
│ Code knowledge     │ Cần               │ Không cần       │
│ Coverage           │ High              │ Low             │
│ Maintenance        │ Medium            │ High            │
│ Real user scenario │ Thấp              │ Cao             │
└────────────────────┴──────────────────┴─────────────────┘

Chiến lược: Kết hợp cả 2 loại
- 70% White-box (Unit tests)
- 30% Black-box (E2E tests)

SLIDE 18: KIỂM THỬ ĐƠN VỊ & CÁC LƯU Ý

Unit Test định nghĩa:
• Kiểm tra 1 function/method độc lập
• Framework: Jest + React Testing Library
• Mục tiêu: Đảm bảo function hoạt động đúng

Unit Test trong dự án:
1. Auth.test.js (14 tests):
   - validateEmail() → TC-UM-006
   - validatePassword() → TC-UM-010
   - validatePhone() → TC-UM-011
   - handleLogin() → TC-UM-002, TC-UM-003, TC-UM-004
   - handleRegister() → TC-UM-008

2. ProductList.test.js (21 tests):
   - filterProducts() → TC-PM-003, TC-PM-004, TC-PM-005, TC-PM-006
   - searchProducts() → TC-PM-002
   - calculateAverageRating() → TC-RS-002
   - sanitizeHTML() → TC-RS-004
   - validateReviewLength() → TC-RS-005

Các lưu ý:
1. Test 1 function/1 case
   ✅ Good: test('should validate email', ...)
   ❌ Bad: test('should validate all fields', ...)

2. Use meaningful test names
   ✅ Good: "should return false for invalid email"
   ❌ Bad: "test email"

3. Arrange-Act-Assert pattern
   ✅ Good:
      const result = validateEmail('test@test.com');
      expect(result).toBe(true);
   ❌ Bad: multiple assertions mixed

4. Mock external dependencies
   ✅ Mock API calls
   ✅ Mock database
   ❌ Don't test external API directly

5. Test edge cases
   ✅ Null, undefined, empty string
   ✅ Boundary values (0, -1, 999999)
   ✅ Special characters

SLIDE 27: LESSONS LEARNED & BEST PRACTICES

Lessons Learned:

1. Testing Strategy:
   ✅ Balanced approach: Unit (70%) + E2E (30%)
   ✅ Risk-based prioritization is effective
   ✅ Black-box + White-box combination works well
   ✅ Test early, test often

2. Test Design:
   ✅ Clear test case IDs & names
   ✅ Comprehensive test data management
   ✅ Equivalence partitioning technique useful
   ✅ Boundary value analysis catches edge cases

3. Test Implementation:
   ✅ Reusable test utilities save time
   ✅ Mock data management is critical
   ✅ Proper error handling in tests
   ✅ Meaningful assertion messages

4. Test Maintenance:
   ✅ Keep tests independent
   ✅ Avoid test interdependencies
   ✅ Regular refactoring needed
   ✅ Documentation is essential

Best Practices for Future Projects:

1. Test Planning:
   - Define test strategy early
   - Create test plan document
   - Estimate effort & timeline
   - Allocate resources properly

2. Test Design:
   - Use test design techniques (boundary, equivalence)
   - Cover positive & negative scenarios
   - Include edge cases & error conditions
   - Validate business rules thoroughly

3. Test Implementation:
   - Keep tests simple & readable
   - Follow Arrange-Act-Assert pattern
   - Use meaningful names
   - DRY principle (Don't Repeat Yourself)

4. Test Execution:
   - Run tests frequently (at least daily)
   - Monitor test performance (execution time)
   - Track test metrics (pass rate, coverage)
   - Keep test environment stable

5. Test Maintenance:
   - Update tests when features change
   - Remove obsolete tests
   - Refactor tests as code evolves
   - Keep test code quality high

6. Documentation:
   - Document test strategy
   - Document test cases
   - Document test data
   - Document troubleshooting guide
